# Conflict resolution playbook

How to resolve conflicts that should **not** be hand-merged like ordinary code. For ordinary source-code conflicts, the rule in SKILL.md applies: understand both intents and combine them. This file is for the special cases where the right move is to regenerate, pick a side deterministically, or handle a non-textual state.

<a name="lockfiles"></a>
## Lockfiles — regenerate, never hand-merge

`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `Cargo.lock`, `Gemfile.lock`, `poetry.lock`, etc.

**Why not hand-merge:** a lockfile is a derived artifact — a resolved dependency graph computed from the manifest files (`package.json`, `Cargo.toml`, …). Hand-stitching two resolved graphs together reliably produces an internally inconsistent lockfile that installs the wrong versions or fails. The lockfile is downstream of the manifests, so resolve the manifests and let the tool recompute the lockfile.

**Procedure:**
1. Resolve any conflicts in the **manifest** files first (`package.json`, `go.mod`, `Cargo.toml`) by hand — those are real source and usually merge cleanly (union of dependencies).
2. Take develop's lockfile as the starting point (it reflects the more recently integrated state), then regenerate against the merged manifests:
   - **pnpm:** `git checkout --theirs pnpm-lock.yaml` then `pnpm install` (reconciles the lockfile with the merged manifests).
   - **npm:** `git checkout --theirs package-lock.json` then `npm install`.
   - **yarn:** `git checkout --theirs yarn.lock` then `yarn install`.
   - **cargo:** `git checkout --theirs Cargo.lock` then `cargo build` (or `cargo update -p <pkg>` as needed).
3. `git add <lockfile>`.
4. Report it as **regenerated**, not as "took theirs" — the final lockfile reflects both sides' dependencies.

If `pnpm install` itself reports a manifest conflict or peer-dependency error, that's a real signal both branches changed the same dependency to incompatible versions — resolve the version in `package.json` deliberately (usually the higher version, unless one side intentionally pinned), then reinstall.

<a name="gomod"></a>
## go.mod — merge requires, then tidy

`go.mod` conflicts are usually two branches adding different `require` entries.

**Procedure:**
1. Hand-merge to the **union** of both sides' `require` / `replace` directives. If the same module appears on both sides at different versions, keep the higher version unless one side has an intentional `replace`/pin.
2. Run `go mod tidy` — this reconciles `go.sum` and prunes anything unused. Don't hand-merge `go.sum` at all; `tidy` rewrites it.
3. `git add go.mod go.sum`.

<a name="generated-files"></a>
## Generated / codegen files — fix the source, re-run the generator

Examples: `*.pb.go` (protobuf), generated mocks, GraphQL/OpenAPI client output, snapshot test files, and in this repo `configs/json/system-capabilities.json` (generated via `make sync-chains`).

**Why not hand-merge:** same logic as lockfiles — these are outputs of a generator. Hand-merging risks a result that doesn't match what the generator would produce, which then breaks the next time anyone regenerates.

**Procedure:**
1. Resolve conflicts in the **source of truth** (the `.proto`, the schema, the `chains.json`, the code being mocked).
2. Re-run the generator (`make sync-chains`, `make generate`, `buf generate`, `go generate ./...`, the mock command, etc.).
3. `git add` the regenerated files.
4. Report as **regenerated**.

If you can't tell what generated a file, look for a header comment ("Code generated by … DO NOT EDIT"), a `//go:generate` directive, or a Makefile target. If you truly can't regenerate it, fall back to careful hand-merge and **flag it in the report** as needing a regenerate-and-verify.

<a name="migrations"></a>
## Database migrations — keep both, fix ordering

Both branches may have added migration files (e.g. `0042_add_x.sql` and `0042_add_y.sql` with the same number, or Go migration entries).

**Procedure:**
1. **Keep both migrations** — each represents a real schema change; neither should be dropped.
2. If they collide on a sequence number/timestamp, renumber the incoming one (develop's, or whichever is conventionally "later") to the next free slot so ordering is unambiguous.
3. If migrations are registered in a list/registry file, include both entries in order.
4. Confirm the two migrations don't touch the same table/column in a contradictory way; if they do, that's a real semantic conflict — flag it.
5. Report as **kept both, renumbered** and call out the renumber explicitly so the user can sanity-check it against any already-applied state.

<a name="deletemodify"></a>
## Delete/modify conflicts (DU / UD)

One side deleted a file the other side modified. `git status` shows `deleted by us`/`deleted by them`.

**Decide based on intent:**
- If the file was deleted because it was **intentionally removed/replaced** (e.g. a refactor moved its contents elsewhere) and the other side's edit is incidental → honor the delete: `git rm <file>`. Then check whether the modification's intent needs to be re-applied at the file's new home.
- If the file is **still needed** and the delete was accidental or the modification is important → keep it: `git add <file>` (after resolving its contents).

Never resolve a delete/modify by reflex — losing a still-referenced file breaks the build, and resurrecting an intentionally-deleted file reintroduces dead code. Verification (Phase 6) catches the first; the report should explain the choice for the second.

<a name="addadd"></a>
## Add/add conflicts (AA)

Both branches created a file at the same path with different content. Treat the contents like an ordinary conflict — combine both intents — unless the two files are unrelated things that happened to land at the same path, in which case one needs renaming. Decide from the content what each was for.

<a name="binary"></a>
## Binary files

Images, fonts, compiled assets. You can't textually merge these, so pick the correct one deliberately:
- `git checkout --theirs <file> && git add <file>` to take develop's version, or `--ours` for the branch's.
- Choose based on which change is the one to keep (e.g. if develop updated a logo and your branch didn't touch it intentionally, take theirs). If both intentionally changed the asset, the binary can only hold one — flag it in the report so the user knows a visual asset choice was made.

<a name="imports"></a>
## Import blocks and formatting-only conflicts

Very common and usually mechanical: both sides added imports, or a formatter reflowed the same region.
- For **import lists**: take the **union** of both sides' imports, then let the language's formatter/organizer settle order (`goimports`, the TS formatter, `prettier`). Don't agonize over import ordering by hand — run the tool.
- For **formatting-only** conflicts (whitespace, reflow, no semantic difference): take either side, then run the repo's formatter (`pnpm prettier:write`, `gofmt`) so the result matches project style. Verify the semantic content is identical between sides before treating it as formatting-only — a real change hiding inside a reformat is easy to miss.
